## 一、先搞懂：Ansible 到底是干嘛的？解决什么痛点？

### 一句话核心定位

Ansible 是**批量运维自动化工具**，本质就是帮你把「一台台机器重复执行的操作」，变成「一条命令/一个剧本批量完成」。

### 对应你当下的场景

你现在有 3 台节点（node1/node2/node3），如果不用 Ansible，你想部署 Nginx 需要做：

1. SSH 登录 node1 → 装软件 → 建目录 → 写页面 → 启动服务
2. SSH 登录 node2 → 重复一模一样的操作
3. SSH 登录 node3 → 再重复一遍

3 台机器就要重复 3 次；如果是 30 台、300 台服务器，手动操作不仅效率极低，还很容易出现「某台漏了一步、配置不一致」的问题。

Ansible 做的事就是：**你只写一次操作步骤，它自动批量在所有目标机器上执行，并且保证每台机器的结果完全一致**。

### 核心价值总结

1. **提效**：批量操作，几十台上百台机器和一台机器的操作成本差不多
2. **一致**：所有节点配置完全统一，不会出现手工操作的疏漏差异
3. **可复用**：操作写成剧本，随时可以重复执行、迁移到新环境
4. **幂等安全**：重复执行不会搞坏系统，比自己写 Shell 循环脚本更稳

> 简单类比： 手动运维 = 挨个给学生发作业 Ansible = 站在讲台上把作业一次性发下去，还能保证每个人拿到的都一样

## 二、两种核心使用方式（对应你已经做过的操作）

Ansible 只有两种用法，你之前都已经实操过，只是可能没明确归类：

### 方式 1：Ad-Hoc 临时命令（单次批量操作）

#### 是什么

一次性的、临时的批量命令，适合快速验证、临时批量操作，相当于「批量版的 Shell 命令」。

#### 语法

```
ansible <目标主机/组> -i <清单文件> -m <模块名> -a <参数>
```

#### 你已经用过的例子

```
# 批量测试所有节点连通性
ansible all -i inventory -m ping

# 批量查看所有节点负载
ansible all -i inventory -m command -a "uptime"

# 批量给 web 组安装 Nginx
ansible web -i inventory -m apk -a "name=nginx state=present"
```

#### 适用场景

- 快速测试连通性
- 临时批量执行命令、采集信息
- 简单的一次性操作（批量装个包、批量看个状态）

---

### 方式 2：Playbook 剧本（复杂流程编排）

#### 是什么

把多个操作步骤按顺序写进一个 YAML 文件里，形成可复用、可追溯的「自动化脚本」，是 Ansible 的主力使用方式。 相当于把一整套部署流程写成说明书，Ansible 照着说明书一步步批量执行。

#### 语法

YAML 格式文件，核心结构：目标主机 + 提权配置 + 任务列表

```
- name: 任务名称
  hosts: 目标分组
  become: 是否提权
  tasks:
    - name: 步骤1
      模块名:
        参数: 值
    - name: 步骤2
      模块名:
        参数: 值
```

#### 你已经用过的例子

你写的 `deploy.yml` 就是典型的 Playbook，把「安装 → 建目录 → 写页面 → 启动 → 验证」一整套流程整合在一起：

```
# 执行剧本，批量完成全流程部署
ansible-playbook -i inventory deploy.yml
```

#### 适用场景

- 完整的服务部署流程
- 复杂的配置管理
- 需要重复执行、长期维护的运维任务
- 需要多人协作、可追溯的标准化操作

## 三、三个核心组成部分（所有操作都围绕它们）

### 1. Inventory 主机清单：告诉 Ansible 管哪些机器

#### 作用

Ansible 的「通讯录」，定义所有被管节点的地址、端口、账号、分组。 你执行命令时指定 `all` 或 `web`，就是从这里面选目标。

#### 你在用的版本

```
[web]
node1 ansible_host=localhost ansible_port=2201
node2 ansible_host=localhost ansible_port=2202
node3 ansible_host=localhost ansible_port=2203

[all:vars]
ansible_user=root
ansible_python_interpreter=/usr/bin/python3
```

- 分组：按角色划分机器，比如 web 组做网站，db 组做数据库
- 变量：统一配置连接参数，不用每台重复写

---

### 2. 模块：Ansible 干活的具体工具

#### 作用

模块就是 Ansible 封装好的「标准化操作单元」，每个模块负责一类事情，天然保证幂等性，比你自己写 Shell 命令更可靠。

#### 你已经用过的常用模块

|模块|作用|对应手动操作|
|---|---|---|
|`ping`|测试 Ansible 连通性|手动 SSH 登录测试|
|`apk` / `yum`|管理软件包|手动执行 apk add / yum install|
|`file`|管理文件/目录|手动 mkdir、chmod|
|`copy`|分发写入文件|手动 vi 写文件、scp 传文件|
|`command` / `shell`|执行 Shell 命令|手动敲命令|
|`uri`|HTTP 请求验证|手动 curl 测试页面|
|`firewalld`|管理防火墙|手动 firewall-cmd 放行端口|

> 核心原则：能不用 shell/command 就不用，优先用官方专用模块，更稳、更符合幂等性。

---

### 3. 幂等性：Ansible 最核心的特性

#### 通俗解释

**同一个操作执行 1 次和执行 100 次，最终效果完全一样，不会重复搞坏系统。**

#### 直观对比

- 手动 Shell：`echo "xxx" >> test.html`，执行十次追加十行，越跑越乱
- Ansible copy 模块：文件内容一致就不修改，执行多少次结果都一样

#### 对你的价值

- 脚本重复执行、定时任务重试，不会把环境搞崩
- 中途失败重试，不会重复安装、重复配置
- 所有节点状态永远一致，不会越跑越乱

## 四、完整使用流程（对应你从 0 到部署 Nginx 的全过程）

你之前踩坑、调试的所有步骤，其实就是 Ansible 的标准使用流程，串起来就是：

### 第 1 步：准备环境

1. 控制端安装 Ansible
2. 被管节点开启 SSH、配置免密登录、安装 Python
3. 验证连通性：`ansible all -m ping`

> 对应你最开始搭建容器节点、配置 inventory、跑 ping 测试的阶段。

### 第 2 步：规划分组与清单

根据业务角色划分主机组，写好 inventory 文件，配置好连接参数。

> 对应你写 web/db 分组、配置 SSH 变量、指定 Python 解释器。

### 第 3 步：选择实现方式

- 简单临时操作 → 用 Ad-Hoc 命令
- 完整部署流程 → 写 Playbook 剧本

### 第 4 步：执行与验证

1. 执行命令 / 剧本
2. 查看执行结果：ok / changed / failed
3. 业务层面验证：确认服务真的可用、配置真的生效

> 对应你执行 deploy.yml、验证页面是否能正常访问的步骤。

### 第 5 步：排错优化

遇到问题从底向上排查： 容器状态 → 端口监听 → SSH 连通 → 服务进程 → 配置文件 → Ansible 配置

> 对应你之前解决容器未启动、路径不对、IPv6 解析、Handler 执行时机等所有踩坑。

## 五、什么时候该用 Ansible？什么时候没必要？

### 值得用的场景

1. **机器数量 ≥ 3 台**：重复操作越多，收益越高
2. **需要保证配置一致**：所有机器环境必须完全相同
3. **操作需要重复执行**：定期部署、批量更新、日常巡检
4. **操作需要可追溯**：有审计要求、需要多人协作

### 没必要用的场景

1. 只有 1 台服务器：手动操作反而更快
2. 一次性的临时操作：用完就扔，没必要写剧本
3. 极其复杂的个性化操作：每台机器都不一样，批量价值低
